# ALFHA ModelHub v0.3.0 release draft

Milestone 11 adds a local proposal-and-review workflow. Select a proposer and
a reviewer, send one task, and receive the initial answer and the review with
separate model IDs, execution IDs, latency, and status. PostgreSQL history
stores each attempted step independently, so a failed review leaves the
proposal available.

- `POST /api/workflows/proposal-review` exposes the workflow. Set
  `OLLAMA_SECONDARY_MODEL` to select two installed local models. Cloud use
  requires explicit opt-in, a fixed free model, and zero-price limits.
  [Windows setup and API example](../README.md#two-model-proposal-and-review)
- The evaluation tools compare the initial proposal, a cross-model review,
  and a same-model review given the exact same saved review prompt. The
  collector verifies each execution against PostgreSQL history.
  [Proposal and review evaluation](proposal-review-evaluation.md)
- A separate offline diagnostic recovered seven passes from 24 previously
  collected Java and SQL submissions after extracting code fences. The
  frozen Milestone 10 campaign retains its original raw scores.
  [Held-out replay](benchmark-repeatability.md#offline-markdown-fence-diagnostic)

## Evaluation findings

All 18 calls in the six-task v2 proposal-and-review batch succeeded. Every
raw response failed strict JSON grading. An offline replay extracted 17
eligible JSON blocks. The Qwen2.5 Coder 3B initial proposal passed two of six
tasks, the 7B review passed one of six, and the 3B same-model review passed one
of five scored tasks. Against the same-model control, the 7B review had one
win, one loss, three ties, and one unavailable pair. These observations cover
one model pair, one attempt per fixture, and a fixed review order.
[v2 batch results](proposal-review-evaluation.md#local-v2-batch-on-8-november-2026)

The workflow is available through the API. The browser still provides chat,
comparison, and history. Review feedback is text, and the workflow has no
tools for executing generated code. Workflow steps use the existing history
schema, with grouping supplied by the workflow response.
